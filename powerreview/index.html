01 项目背景

电力试验报告审核：人工逐页核对的时代该结束了

全国电力行业每年产生数百万份试验报告，每份需经多级人工审核。然而，审核人80%时间花在格式规范、数据合格的"正常报告"上，真正需要专业判断的异常报告反而得不到足够关注——这是结构性效率灾难。

行业现状
  • 电力试验报告审核是电网安全的"守门员"
  • 每份报告需经技术员→一级审核→总工三级审核
  • 审核依赖人工逐页对照DL/T 596、GB 50150等标准
  • 温度修正系数查表易出错，占返工原因60%
  • 旺季报告堆积，审核人连续工作导致漏审风险
核心痛点
  • 审核疲劳漏审：80%时间看合格报告，异常报告反被忽略
  • 温度修正查错：不同设备不同公式，手算+查表占返工60%
  • 数据结论矛盾：数据超标结论却写合格，最致命的漏审场景
  • 标准翻查耗时：多标准交叉冲突，人工翻查平均10分钟
  • 签字追责风险：审核签字终身负责，AI判定不可溯源不敢用

为什么是AI预审而不是传统数字化？传统方案（表单+流程引擎）只能解决"流程效率"问题，但无法解决"判断质量"——判据自动比对、温度修正计算、数据-结论一致性校验，这些都需要标准知识图谱+规则引擎推理。AI产品经理的核心挑战在于：AI做预审，人做终审——既要让AI判断足够准，又要让审核人敢信任AI的判断——这就是AI信任边界问题，也是贯穿本项目的主线。

03 用户场景与痛点映射 · Scenario × Pain Point

5个核心场景，21个痛点，每个痛点都有真实场景锚定

痛点脱离场景就是空洞的数据。用Scenario-Based Analysis把每个痛点锚定到真实工作场景，让需求从场景中生长而非从假设中推导。

场景1 · 春检高峰期批量审核
用户画像: 李建华 · 技术专责 · 日均8-10份报告
春检期间李建华每天收到8-10份试验报告，80%是格式合格、数据正常的报告，但他必须逐项审核才能确认。连续审核5份后视觉疲劳加剧，曾漏过介损超标0.05%的临界案例。这就是80/20困境的典型场景。
收到8份报告→ 逐项手动审核→ 第5份后疲劳→ 漏审临界异常
P01: 审核疲劳导致漏审 · P05: 标准条款翻查耗时 · P14: 格式错误反复核验
方案: AI预审筛掉80%合格报告 + 异常看板Critical/Warning/Info分级 + 只看AI flagged异常项 → 审核效率提升60%，漏审率0%

场景2 · 温度修正系数查错导致系统性偏差
用户画像: 张磊 · 技术员 · 变压器介损试验
张磊在做变压器介损试验时，需要将实测值按DL/T 596附录D修正到20°C基准值。修正系数表按设备型号+绝缘介质+温度区间分多行，查错一行导致整批次数据偏差。这种错误占返工原因的60%。

AI技术方案 AI Architecture

不迷信单一路线。Rule Engine 处理确定性判据（100%可解释），Knowledge Graph 构建设备-试验-标准关系网络，NLP 处理非结构化文本校验。三层协同，优雅降级 保底。

双引擎架构：Rule Engine + Knowledge Graph

Rule Engine（规则引擎）
  • 自研JSON规则库，确定性判据→100%可解释
  • 覆盖GB 50150/DL/T 596核心判据 = 48组规则族
  • 每条规则映射标准条款号
  • 优先级最高，KG/NLP不可覆盖
  • 执行延迟 <50ms，满足实时反馈
Knowledge Graph（知识图谱）
  • 设备-试验-标准 三元组关系
  • 跨设备类型关联推理（如变压器→套管）
  • 历史数据趋势分析图谱
  • 支撑L2语义验证、L3智能推理
  • 图谱规模：2,000+实体、8,000+关系
技术栈：前端 Vue3+ElementPlus · 网关 Nginx反向代理 · 后端 Python/FastAPI(uvicorn) · 数据库 PostgreSQL/SQLite · Excel解析 openpyxl+模板匹配 · 规则引擎 自研JSON规则库 · ML分类器 LightGBM/XGBoost · NLP Sentence-BERT · 历史对比 时序数据库 · 趋势分析 线性回归+异常检测 · 安全 TLS 1.3+AES-256 · 部署 Docker+K8s私有化内网
NLP Module（自然语言处理）

数据-结论一致性校验。基于Sentence-BERT语义相似度，识别"数据超标但结论合格"的语义矛盾。置信度阈值0.85。

ML Classifier（机器学习分类器）

LightGBM/XGBoost，补充规则引擎模糊场景。当规则无法精确匹配时，ML提供概率判断，置信度<0.6自动降级为L3人工审核。

LLM（可选）：本地部署，仅用于生成建议文本（如审核意见草稿），不参与判据比对核心链路。依据D-01决策：端到端AI在该场景TRL=3-4，不用于判定。

三级AI能力 + 优雅降级

L1 Rule
规则匹配 — 确定性判据比对

直接比对试验数据与标准限值。温度修正、绝缘电阻、介质损耗等确定性指标。输出：合格/超标 + 标准条款号。100%可解释，无需降级。

L2 Semantic
语义验证 — 数据-结论一致性

NLP语义比对试验数据与结论描述，识别逻辑矛盾。L2细分（v2.0+）：L2a(5%-7%)AI建议通过+建议确认，审核人扫一眼即可；L2b(7%-10%)人工必审+历史趋势+参考依据。L2a释放约40%审核压力。优雅降级：L2失败不影响L1输出。

L3 Reason
智能推理 — 跨试验关联分析（v1.1+）

基于KG的跨设备、跨试验关联推理。如：变压器油色谱异常+绕组变形→疑似绕组过热。Technology Readiness不足，v1.0降级为L1+L2。

优雅降级 Chain：L3 降级 → L2 结果 + 人工提示  |  L2 降级 → L1 结果 + 人工提示  |  L1 不会失败（确定性规则）  |  任何降级都明确告知审核人

Cold Start 策略：规则先行，数据飞轮驱动演进

Phase 0 · 种子规则库（Day 1即可用）

从GB 50150 + DL/T 596硬编码48组核心规则族。无需历史数据，Day 1即可交付审核价值。规则覆盖预防性试验最高频的4类设备（变压器、断路器、GIS、互感器）。

Phase 1 · 知识图谱冷启动（Month 1-3）

从标准文档结构化抽取实体和关系，构建种子图谱（2,000+实体）。同步收集审核人的修正反馈，用于图谱校准。Human-in-the-Loop保证冷启动期质量。

Phase 2 · 数据飞轮启动（Month 3-6）

审核反馈 → 规则优化 → 准确率提升 → 用户信任增加 → 更多报告使用 → 更多反馈。数据飞轮形成正循环。预计6个月达到L2语义验证的置信度阈值。

AI信任模型 AI Trust Framework

电力行业对AI的信任是零基的。不信任不是因为AI不够好，是因为后果不可承受。三层信任模型从"可用"到"可信"到"可靠"，逐层构建。

可用层 · 透明

每个AI判定结果附带完整推导链：标准号→条款→限值→实测值→判定。审核人随时可审查AI的"思考过程"。

"我不需要你替我判断，我需要你能让我快速验证你的判断" —— 审核人访谈

可信层 · Accountability

AI辅助但不决策。最终签字权始终在人。AI标记异常 → 人确认 → 签字归档。Audit Trail全程留痕：谁审的、AI说了什么、人做了什么判断。

产品红线：不替代签字 —— AI是Co-Pilot，不是Auto-Pilot

可靠层 · Resilience

优雅降级：L3失败降L2、L2失败降L1、L1不会失败。任何降级都明确告知审核人。系统故障不影响审核流程——最差情况退回手动审核。

降级不等于失败 —— 让审核人知道AI的边界，比假装没有边界更安全

北极星指标
AI预审准确率 ≥90%

产品决策 Decision Records

关键决策的Why和Trade-off。不是为了记录结论，而是为了让未来的自己理解当时为什么这么做——避免Hindsight Bias。

D-01 规则引擎优先，而非端到端AI

决策：v1.0采用Rule Engine + Knowledge Graph，不用端到端LLM做判据比对。
Trade-off：牺牲了灵活性（新设备需要手动添加规则），换取了100%可解释性和确定性。
Why：电力审核对"AI黑箱判断"零容忍。判据比对必须可追溯到标准条款号，LLM无法保证这点。Technology Readiness评估：端到端AI在该场景的TRL等级仅为3-4，规则引擎TRL=9。

D-02 只做4类设备，不做全品类

决策：v1.0只覆盖变压器、断路器、GIS、互感器4类主设备。
Trade-off：覆盖面窄（4/20+设备类型），但单类深度足够。
Why：残酷取舍——4类设备占审核工作量80%以上（80/20 Rule）。电缆、电容器等虽多但单项审核简单，人工审核已足够。先做最难最有价值的。

D-03 私有化部署，不做SaaS

决策：仅支持私有化部署，不提供SaaS公有云服务。
Trade-off：放弃了中小企业市场（SaaS更容易推广），但赢得了大型电力企业的信任。
Why：电力企业有"数据不出网"的硬性合规要求。SaaS模式下试验数据上云，直接违反安全规定。这是Deal-Breaker，不是Feature。

D-04 v1.0与PMS互补，v2.0审批流集成

决策：v1.0不建审批流转，定位为PMS的审核增强层；v2.0根据用户反馈主动集成审批流。
Trade-off：v1.0依赖PMS完成审批闭环，本产品不独立闭环；v2.0从"独立工具"升级为"工作流节点"。
Why：v1.0阶段国网PMS已全面部署，替代PMS会遭遇切换成本阻力，"Complement not Compete"降低采购门槛。但v2.0用户反馈明确——"AI审得再快，还要手动把结果抄到OA里"，审批流集成是用户驱动而非产品臆想。决策演进证明：好的产品决策是动态校准的，不是一成不变的。

D-05 一致性校验用NLP而非纯规则

决策：数据-结论一致性校验采用NLP语义比对，而非穷举规则模板。
Trade-off：NLP有误判风险（置信度阈值0.85），但覆盖面远超模板匹配。
Why：结论描述的表述方式千差万别，穷举模板Polymerization Problem严重——10种设备×5种结论格式=50套模板，维护成本爆炸。NLP以一套模型覆盖所有表述，配合优雅降级控制风险。

D-06 L2层细分，而非L2整体升级

决策：v2.0将L2语义验证层细分为L2a(5%-7%)和L2b(7%-10%)，而非整体提升L2的置信度阈值。
Trade-off：增加了系统复杂度（三级变四级判定），但释放了约40%的L2场景审核压力。
Why：推理模型进步缩小了"不可靠"的范围，但没消除"不可靠"本身。L2a细分是精细校准而非推翻重做——好的架构是能容纳技术演进的，L2层的细分正是三级信任模型弹性的体现。

D-07 Qwen3升级时机：v2.1而非v2.0

决策：Qwen3发布后不在v2.0立即升级，而是在v2.1做Agent层升级。
Trade-off：v2.0的Agent层仍用Qwen2.5-72B，不是最新模型；但保证了v2.0的稳定性优先。
Why：Agent层处理的是20%的模糊场景，核心准确率由规则引擎决定。先让v2.0的批量审核+审批流稳定运行收集数据，再在v2.1升级Agent层——不追新，只追稳。产品决策不是押注某一代模型的能力，而是设计一个能容纳技术演进的架构。
